# Stage 09 - Continuous delivery

**Tag:** `stage-09` · **Files:** `deploy.yml`, `resolve-release.yml`, `rollback.yml`, `deploy/**`, `runner/**`,
`scripts/setup-environments.ps1`, `docs/deployment.md`, `docs/self-hosted-runner.md`

## The flow

```
release.yml ──workflow_call──▶ deploy.yml
   resolve     (hosted)  tag -> digest, cosign verify, gh attestation verify
   staging     (hosted)  docker compose up -> smoke -> down          environment: staging
   production  (laptop)  approval -> blue-green -> smoke -> rollback? environment: production
```

## Environments

`scripts/setup-environments.ps1` creates:

* **staging** - no reviewer, deployable only from `main`.
* **production** - required reviewer `gagan046-dev`, deployable only from `main` and `v*` tags.
  The run pauses with "Waiting for review"; approve in the UI or:

```powershell
gh api repos/gagan046-dev/pipelinedoctor/actions/runs/<run-id>/pending_deployments --jq '.[].environment | {id, name}'
gh api -X POST repos/gagan046-dev/pipelinedoctor/actions/runs/<run-id>/pending_deployments -F "environment_ids[]=<env-id>" -f state=approved -f comment="ship it"
```

A job with `environment:` makes GitHub create a **Deployment** with statuses
(`in_progress`, `success`, `failure`). `deploy/scripts/annotate-deployment.sh` adds one more
status with `pd:kind=deploy;version=...;color=...;outcome=...`, which the Console turns into
**DORA metrics** (deployment frequency, lead time, change failure rate, time to restore).

## Digests, not tags

`resolve` turns `pipelinedoctor-console:0.2.0` into `pipelinedoctor-console@sha256:...` and
verifies signature + provenance **on a GitHub-hosted runner**. Staging and production then run
exactly those bytes; a tag moved in between cannot change what is deployed.

`resolve` is a **reusable workflow** (`resolve-release.yml`) called by both `deploy.yml` and
`rollback.yml`. A rollback to a version is a deploy of an older release, so it passes the same
gate: there is no path to the laptop that skips signature, provenance and digest pinning.

## Ephemeral staging

The staging "server" is the hosted runner itself: `docker compose up --wait` starts proxy and
console, `smoke.sh` runs `python -m pipelinedoctor_console.smoke` **inside the compose network**
(no host ports), and `down -v` deletes everything. Production is only reachable through a green
staging job.

## Blue-green with automatic rollback (production)

1. Start the idle colour with the new image, wait for its health check.
2. Switch nginx to it (`switch-color.sh`, `nginx -s reload` = no dropped connections).
3. Smoke test through the proxy + a short soak.
4. Fail -> switch back to the old colour automatically, job fails, outcome `auto_rolled_back`.
5. Pass -> stop (not remove) the old colour: an instant manual rollback stays possible.

## Self-hosted runner on a public repository

The production job runs on the laptop (`runs-on: [self-hosted, pd-prod]`). Anyone can open a
PR on a public repo, so: only `deploy.yml/production` and `rollback.yml/rollback` may use the
label, neither has PR triggers (policy rule R3, required check), both need the production
approval, the environment only accepts `main`/`v*`. Details and residual risk:
[security.md](../security.md), [self-hosted-runner.md](../self-hosted-runner.md).

## Commands

```powershell
gh workflow run deploy.yml -f version=0.2.0 -f environment=staging
gh workflow run deploy.yml -f version=0.2.0 -f environment=production
gh workflow run rollback.yml -f reason="smoke ok but users see 500s"
gh workflow run rollback.yml -f version=0.1.0 -f reason="bad release"
gh api "repos/gagan046-dev/pipelinedoctor/deployments?environment=production" --jq '.[] | {id, ref, created_at}'
gh api repos/gagan046-dev/pipelinedoctor/actions/runners --jq '.runners[] | {name, status, labels: [.labels[].name]}'
```
